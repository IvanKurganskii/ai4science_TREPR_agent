# Граф знаний и онтология

Версия: 2026-11-08.1. Корень проекта — каталог с [AGENTS.md](../AGENTS.md).
Этот модуль обязателен при условиях из таблицы в AGENTS.md; прочитай его полностью
до соответствующей работы. Общие запреты и порядок загрузки из AGENTS.md сохраняются. Выполняй только то,
что входит в запрос: чтение процедуры не поручает запускать расчёты или менять данные.
Режим определяй по AGENTS.md. В СПРАВКА применяй только чтение, поиск и ограничения:
пункты о записях, загрузках, расчётах и проверках результата не исполняй. Их чтение
не разрешает менять режим. Следующие рабочие процедуры относятся к ЗАДАЧА.
Ссылки на номера разделов относятся к AGENTS.md, если не указано иное.

### 2.1. Хранилище

В ЗАДАЧА создай в `.obsidian/` два файла, если это необходимо. В СПРАВКА настройки
только читай; отсутствующие настройки опиши в ответе. Если файл уже есть (его создаёт Obsidian при первом
открытии папки), допиши в него недостающие ключи, остальное не трогай.

`.obsidian/app.json` — Obsidian показывает все файлы проекта, включая данные и код:

```json
{"showUnsupportedFiles": true}
```

`.obsidian/graph.json` — вид «Граф» показывает файлы и раскрашивает узлы:

```json

 ]}
```

### 2.2. Онтология в графе

`ontology.yaml` — схема: классы, отношения, атрибуты и правила. До работы с узлами
загрузи записи по текущему этапу из [ontology-context](ontology-context.md).
При очистке/численном подборе достаточно служебных классов и их правил;
квантовые определения и предметные карточки — при интерпретирующем отчёте.
Для фактически описываемых классов нужны надклассы и применимые правила.
Всю схему в контекст не загружай,
если запрос не требует работы со всей схемой. Полное чтение YAML программой
для проверки или генерации допустимо; её вывод должен оставаться кратким.

Для каждого класса схемы должна существовать заметка `ontology/<Класс>.md`:

```
---
kind: класс
---
# <Класс>

<определение из ontology.yaml>

Отношения от этого класса: <отношения, у которых класс в domain>.
Атрибуты: <атрибуты, у которых класс в domain, с допустимыми значениями>.

## Связи
- подклассОт: [[<надкласс>]]
```

У верхних классов (`parent: null`) раздел «Связи» пустой; при нескольких надклассах
сохраняй каждую связь. Карточки — производные от схемы, без полного блока rules.
При необходимости в ЗАДАЧА проверь актуальность выбранных карточек:
`../.mars_env/bin/python "/mnt/c/Users/kurga/OneDrive/Документы/YSDA/checks/gen_ontology_notes.py" --root "$PWD" --check --class Задача` (повторяй `--class`
для остальных). Для разрешённого обновления карточек убери `--check`.
Схему не меняй ради карточек. В СПРАВКА при расхождении используй YAML и сообщи
о нём; карточки не исправляй. Это не требует чтения всех карточек в контекст.

### 2.3. Заметки об объектах

Каждый объект работы — заметка `notes/<название>.md`:

```
---
type: <Класс>
---
# <название>

<2–4 строки: что это, откуда взято, числа с единицами>

## Связи
- тип: [[<Класс>]]
- <отношение>: [[<название другой заметки>]]
- хранитсяВ: [[<путь к файлу от корня проекта>]]
```

Правила (запись только в ЗАДАЧА; в СПРАВКА — чтение существующих узлов):
- Название называет экземпляр: «Fit\_<Experiment\_name>_<integration\_window>\_YEAR-MONTH-DAY\_v#» для 1d фита, «Fit\_<Experiment\_name\_YEAR-MONTH-DAY\_v#» для 2d-fit; «spec\_<Experiment\_name>_<integration\_window>\_YEAR-MONTH-DAY\_v#» для среза по магнитному полю; «kin\_<Experiment\_name>_<integration\_window_in_G>\_YEAR-MONTH-DAY\_v#» для кинетик. Не использовать названия классов для названия заметок.
- В названии нет символов `/ \ : # | [ ]`: пиши «кДж на моль», «ln k от 1 на T».
  Символ `/` создаёт вложенную папку, и ссылки на заметку ломаются.
- Строка `- тип: [[<Класс>]]` обязательна: она связывает объект с его классом в графе.
- Остальные связи — только отношения из `ontology.yaml`, от области определения к
  области значений. Связь записывается в заметке, от которой она идёт. Проверяй
  domain/range с учётом надклассов, тип целевого объекта и существование файла или
  заметки. Новое имя отношения или похожая формулировка не заменяет свойство схемы.
- Для новых и изменённых узлов проверь соответствие `type` классу онтологии и
  каждую связь. Например, событие запуска тестов описывается как `Проверка`, а
  описание способа проверки — как `Метод`; допустимые связи у этих классов различаются.
- Файлы проекта — данные, код, результаты, отчёты, тексты источников в `library/` —  отдельные заметки не получают: на них ссылаются по пути от корня, например
  `[[data/raw/rates.csv]]`, `[[src/fit.py]]`, `[[library/arrhenius_1889.md]]`.
- Источник — заметка `notes/<автор год>.md` с типом `Источник` и связью
  `хранитсяВ: [[library/…]]`. Связи `основанаНа` и `ссылаетсяНа` ведут к заметке
  источника; к файлу в `library/` ведёт только `хранитсяВ`.
- Отдельный отчёт в `reports/` пишется, только если пользователь просил отчёт.
  Это ограничение не относится к обязательному журналу `diary.md` из раздела 6.
  Отчёт — сам файл `reports/<название>.md`: в начале `type: Отчёт`, в конце раздел
  «Связи», как у заметок объектов. В тексте отчёта утверждение, взятое из источника,
  сопровождается ссылкой на заметку источника: «… [[Laidler 1984]] ».
- Ссылки `[[…]]` в тексте заметок не берутся в обратные кавычки: внутри кода Obsidian
  их не показывает.
- Каждый ВР ЭПР эксперимент — отдельная заметка типа `ВРЭПРэксперимент`.
  Свяжи его отношением `применяет` с конкретным методом `ВРЭПРспектроскопия`,
  отношением `выход` — с полученными `ВРЭПРданные`. Данные связаны отношением
  `хранитсяВ` с исходным файлом и `полученВ` с экспериментом. Сам процесс не
  хранится в CSV. Если подтверждены физический образец и общая серия опытов,
  используй `исследует` → `Образец` и `входитВ` → `СерияЭкспериментов`;
  не подменяй серию процессов набором данных. Расчёт использует входные наборы
  данных через `использует`, а срез или обработанный набор указывает исходный
  через `вычисленИз`. Не придумывай образец, гипотезу или параметры установки
  ради прохождения проверки: отсутствующие сведения перечисляй явно.
- Если для объекта нет подходящего класса или отношения в онтологии, запиши
  предложение «Новый тип: <почему>» или «Новое отношение: <почему>» в задаче и дневнике.
  Не выдавай несуществующий `type` или связь за узел, прошедший проверку. Если без
  расширения схемы нельзя закончить задачу, зафиксируй блокировку и запрос решения.
  `ontology.yaml` не меняй: решение о расширении схемы принимает пользователь.
- В ЗАДАЧА заметку создавай при появлении подтверждённого объекта: набор данных —
  при чтении, метод — при выборе, результат — после расчёта, проверку — после проверки.
  На техническом этапе сохраняй служебные узлы/файлы/метрики; развёрнутые предметные
  карточки параметров и физическую интерпретацию отложи до отчёта и нужной загрузки.
  Одно чтение в СПРАВКА новых узлов не создаёт. Если новых предметных фактов нет,
  используй подтверждённые существующие связи, результат задачи и пояснение в дневнике;
  не придумывай научные сущности или связи ради обязательного «пополнения графа».
- Реальная заметка, закрывающая подзадачу, ссылается на неё: эксперимент/проверка —
  `решает`, отчёт — `выполняет`. Для чистого анализа допустим результат в самой задаче
  по workflow; отдельный закрывающий узел не создавай искусственно.
