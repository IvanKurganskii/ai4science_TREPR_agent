# Методика проверки файлов очищенных спектров и срезов



## 0. Паспорт

| Поле | Значение |
|---|---|
| Задача | Проверить наличие, текстовую структуру и конечный ненулевой сигнал в выходных файлах обработки |
| Дисциплина | Физика, обработка экспериментальных спектров |
| Ветка верификатора | Договор о файлах данных с контролируемыми нарушениями |
| Дата записи | 2026-11-08; фактический коммит вносит автор после просмотра |
| Область | Очищенные 2D-спектры и 1D-срезы; качество самого алгоритма очистки отдельно не проверяется |
| История | Прежняя очистка/проверки уже проводились; новая серия демонстрации ещё не запускалась |
| Метка плана | Предлагается `exp-methods-v1`; `hw2` относится к готовому пакету |


## 1. Замысел

- Вопрос: способны ли проверки отличать структурно допустимые выходные
  спектры от отсутствующих, пустых, нулевых или содержащих NaN/Inf файлов?
- Гипотеза: скрипты отвергают каждый перечисленный дефект и принимают
  контрольные корректные файлы, не считая координатные оси интенсивностями.
- Ответ: коды 0/1, полные диагностические сообщения, таблица ожидаемых и
  фактических вердиктов на корректном наборе и отдельных нарушениях.
- Базовая линия: слабая проверка только наличия/количества файлов. На том же
  наборе она пропускает числовые дефекты. Это план контрольного сравнения,
  код/новые результаты базовой линии ещё не подготовлены.

## 2. Постановка

| Что | Фиксация |
|---|---|
| Меняем | Ровно один дефект в копии контрольного набора; локализация в processed или slices |
| Фиксируем | Версию проверок, набор расширений, исходные файлы, layout и ожидаемые вердикты |
| Случайность | Синтетический ненулевой сигнал для seed=101,202,303; одинаковые наборы у базовой и полной проверок |
| Формат processed | grid: первая числовая строка и первый столбец — координаты, остальная матрица — интенсивности |
| Формат slices | rows: две числовые строки — поле и интенсивность; columns испытывается отдельно с явной опцией |
| Измеряем | Код, этап и текст причины отказа, число ложных допусков/отказов, время; размеры файлов не являются интенсивностями |
| Единицы тестовых файлов | Поле G, время ns; указывать в текстовой шапке, но не приписывать скриптам семантическую проверку этих единиц |
| Что не меняем | Исходные реальные спектры, существующие очищенные карты и срезы, критерии после наблюдения вердиктов |

Границы именно технические: любое конечное ненулевое число допустимо как
интенсивность. Порог амплитуды, SNR, время появления сигнала, физические
диапазоны поля и качество подавления шума этими скриптами не задаются.

| Свойство договора | Текущая реализация |
|---|---|
| Исходные спектры существуют, набор непуст | Оба скрипта |
| Число processed равно числу raw для каждого расширения | Оба скрипта |

| Есть числовые данные, строки имеют согласованную ширину | check_signal для заявленного layout |
| Все числовые значения конечны | NaN, +Inf и -Inf отвергаются, включая координаты |
| Есть хотя бы одна ненулевая интенсивность | Координаты исключаются; положительные поля не «спасают» нулевой сигнал |
| Layout среза согласован | rows требует ровно две числовые строки, columns — две колонки |


## 4. Код и окружение

Верификатор: `spectra_cleaned.py`, `spectra_sliced.py`; второй импортирует
вспомогательные функции первого. Используется стандартная библиотека Python.
Наблюдённая рабочая среда — WSL, Python 3.11.16. Для синтетических примеров
предусмотрен NumPy 2.4.6, но сами эти две проверки от NumPy не зависят.


Из корня проекта задать PYTHON (локально ../.mars_env/bin/python), CHECKS_DIR
(локально ../../checks; в пакете checks), RAW_DIR и SPECTRA_DIR. Для текущих
реальных данных RAW_DIR=data/raw_spectra, SPECTRA_DIR=results/spectra; для
контролируемых нарушений указать только соответствующий экспериментальный набор.

Одна составная команда проверки полного корректного набора:

```bash
"$PYTHON" "$CHECKS_DIR/spectra_cleaned.py" "$SPECTRA_DIR" \
  --raw-dir "$RAW_DIR" --layout grid &&
"$PYTHON" "$CHECKS_DIR/spectra_sliced.py" "$SPECTRA_DIR" \
  --raw-dir "$RAW_DIR" --layout rows
```

Код 0 — обе проверки прошли. При ошибке первого скрипта второй через &&
не запускается; для карты ошибок отрицательного примера запускать нужный
скрипт отдельно и записывать его реальный код. Обычный отказ — код 1;
ошибка интерфейса/исключение не считается успешным обнаружением свойства.
Вывод и код сохранять без маскировки через `| tail` без pipefail.

При подготовке среды для самой очистки используют дополнительные библиотеки
из src/mars_cleaning; проверка наличия файлов не подтверждает работу этих
библиотек. Включение кода и данных в самодостаточный пакет ещё предстоит.

## 5. Сценарии проверки и показ ошибки

Каждый сценарий повторить на трёх seed. Версия верификаторов и список
ожидаемых ответов фиксируются до запуска. «До» и «после» — отдельные наборы,
не исправление оригинального экспериментального файла на месте.

| Сценарий | Ожидаемый результат |
|---|---|
| Корректные grid processed и rows slices с шапками | Обе проверки 0 |
| Один processed отсутствует, остальное неизменно | Отказ по числу processed |
| Срезов меньше требуемого числа, processed корректны | Отказ spectra_sliced по числу slices |
| Файл пуст или содержит только шапку | Отказ по отсутствию числовых данных |
| Удалена шапка, числа сохранены | Отказ по отсутствию текстовой шапки |
| Все интенсивности равны нулю при ненулевых координатах | Отказ по нулевому сигналу |
| Ровно одна NaN в числовых данных | Отказ по неконечному значению |
| Ровно одна +Inf либо -Inf | Отказ по неконечному значению, отдельные случаи |
| Числовая строка имеет другую длину | Отказ по структуре |
| Третья числовая строка в rows-срезе или не две колонки в columns | Отказ по layout |
| Служебный JSON добавлен к корректному набору | Вердикт и числа спектров не меняются |
| UTF-8 BOM и пустые строки перед корректной шапкой | Корректный пример по-прежнему принимается |


## 6. Шаги глубины

| Шаг | Действие | Условие перехода |
|---|---|---|
| Фиксация | Коммит методики, версий скриптов, рецепта и ожидаемых вердиктов | Коммит раньше новых результатов |
| Пробный | Корректный синтетический набор seed=101 | Обе проверки 0, пути и layout однозначны |
| Короткая проверка | Нулевой сигнал, NaN и отсутствующий файл | Нужные скрипты отвергают каждый дефект с правильной причиной |
| Полная демонстрация | Все сценарии для seed=101,202,303 и базовая линия | Сохранены команды, коды и вывод для всех случаев |
| Реальные данные | Чтение текущих raw/processed/slices обеими проверками | Вердикт записан как есть, исходные файлы не изменены |
| Итог | Сводная таблица, «до/после», ограничения | Выполнено правило раздела 7 |

Дерево подцелей: технически допустимый результат → (1) полнота наборов;
(2) текстовая и числовая структура; (3) конечность значений;
(4) ненулевой именно сигнал; (5) корректный отказ на известных нарушениях.
После третьей неудачной попытки одного шага остановиться и разобраться с
причиной. Три одинаковых запуска без исправления причины не являются прогрессом.

## 7. Правило принятия до запуска

1. Корректные примеры обоими скриптами принимаются для всех трёх seed;
   предусмотренные повреждения отвергаются соответствующим этапом с кодом 1
   и ожидаемой диагностикой. Ложных допусков и отказов на этом конечном наборе — 0.
2. Для одного и того же входа повторный запуск даёт тот же вердикт. Три seed
   меняют исходные ненулевые интенсивности, а не критерии и не исходную схему.
3. На одинаковых повреждённых файлах сравнить базовую и полную проверки:
   показать хотя бы один ложный допуск базовой линии и его обнаружение полной.
   Показать обратный переход к корректному набору без изменения верификатора.
4. Для текущих реальных данных критерий только технический: обе команды 0.
   Если обнаружен дефект, результат — «не пройдено», без автоматической
   перегенерации/исправления исходных спектров. Исправление — отдельная задача.
5. По seed сохранить таблицу кодов/причин, количества ошибок и диапазон min–max
   времени. Отсутствие разброса детерминированного вердикта не выдаётся за
   доверительный интервал качества очистки или за оценку частоты всех возможных ошибок.
6. В научном отчёте не делается статистическое утверждение об улучшении SNR
   либо сохранении формы: эти величины данным верификатором не измеряются.
7. Любое расхождение с ожидаемым ответом, исключение, отсутствие исходных
   файлов или расхождение версий останавливает серию до разбора. Ослабление
   правил требует новой версии методики и нового плана до новых запусков.

## 8. Бюджет

Синтетическая серия — до 10 минут; реальные текстовые файлы — до 10 минут
на обе проверки. Сохранять фактическое время, не объявлять тайм-аут успехом.
LLM не вызывается на каждый элемент массива/сценарий. В контекст выводить
сводку и ошибки; целевой бюджет агента до 200000 токенов на серию, остановка
при остатке дневного бюджета менее 500000.

## 10. Ограничения

Проверки не восстанавливают очистку из исходных данных, не сравнивают численно
родителя и срез, не проверяют сохранение формы/пиков, правильность фонового
окна, SVD-ранга, интегрирования или метаданных. Непустая шапка не доказывает
наличия всех требуемых записей. Совпадение количеств не устанавливает взаимно
однозначное происхождение файлов. Произвольный конечный шумовой массив
может пройти технический договор. Для физической проверки и полноты
происхождения нужны дополнительные независимые проверки с собственной методикой.
Коды 0 этих двух скриптов нельзя называть подтверждением качества очистки. 
Тесты пока проверяют, что все спектры очищены от базовой линии, сэмплированной до вспышки лазера, 
и что для каждого получен один корректный срез. Служебная проверка перед работой
