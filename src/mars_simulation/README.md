# MaRS-epr: инструменты моделирования для агента

Шесть Python-инструментов и JSON-схем для function/tool calling в агентах на DeepSeek V4 Flash и Qwen3.6. Код не зависит от SDK провайдера: агент передаёт имя функции и JSON-аргументы, приложение вызывает `dispatch()`, затем возвращает результат агенту.

Источник моделей — `Fit Dir/rho-ndi_fit.ipynb`: high-J spin Hamiltonian / Context / 1D / 2D и Moderate J Model / Fit 1d / Fit 2d. Notebook при вызове инструментов не выполняется; виджеты и глобальные переменные не нужны.

## Выбор инструмента

| Инструмент | Расчёт | Входные параметры |
|---|---|---|
| `simulate_high_j_1d` | Стационарный полевой спектр эффективного S = 1 | Гамильтониан, начальные веса |
| `simulate_moderate_j_1d` | Стационарный полевой спектр двух S = 1/2 | Гамильтониан, начальные веса |
| `simulate_high_j_2d` | Кинетика при фиксированной high-J модели | `spin_model` из результата 1D/full, контекст |
| `simulate_moderate_j_2d` | Кинетика при фиксированной moderate-J модели | `spin_model` из результата 1D/full, контекст |
| `simulate_high_j_2d_full` | Временной спектр с явно заданными гамильтонианом и контекстом | Гамильтониан, контекст, настройки |
| `simulate_moderate_j_2d_full` | То же для двух взаимодействующих электронов | Гамильтониан, контекст, настройки |

`2d_full` обозначает доступность всех спиновых и кинетических параметров. Он использует тот же физический расчёт `CoupledTimeSpectra`, что и `2d`, и не запускает оптимизацию. `spin_model` — переносимый JSON-объект, поэтому обычный `2d` можно вызвать в новом процессе. В нём разрешён отдельный `device`, чтобы перенести расчёт CPU ↔ CUDA; сетка и физические параметры остаются из снимка. Для их изменения используйте `2d_full`.

## Подключение

Из корня проекта:

```python
import json
from src.mars_simulation import MarsSimulationTools

tools = MarsSimulationTools(output_dir="results/mars_simulations")
function_schemas = tools.schemas  # Передайте в список tools вашего агента.

# Для каждого function call, полученного от модели:
result = tools.dispatch(function_name, function_arguments)
tool_result_text = json.dumps(result, ensure_ascii=False, allow_nan=False)
# Верните tool_result_text в ответе инструмента с исходным tool_call_id.
```

`function_arguments` может быть словарём или JSON-строкой. `dispatch` возвращает `ok: false` и сообщение при ошибке; прямые Python-вызовы `tools.simulate_high_j_1d(...)` и другие методы выбрасывают исключения. Не передавайте агенту другие методы объекта. Схемы также лежат в `tool_schemas.json`; инструкция для системного промпта — в `AGENT_GUIDE.md`.

Если `src` включён в `PYTHONPATH`, можно импортировать `from mars_simulation import ...`. Для собственного численного кода есть `SimulationEngine.simulate(...)`: он принимает явные массивы осей, возвращает numpy-массивы без создания файлов. Смотрите `examples/workflow.py`.

CLI для одного вызова:

```powershell
python -m src.mars_simulation --request src/mars_simulation/examples/high_j_2d_full.json --output-dir results/mars_simulations
python -m src.mars_simulation --schemas
```

Опциональный `--serve` читает по одной строке `{"id":"call_1","name":"simulate_high_j_1d","arguments":{...}}` и выдаёт по одной JSON-строке `{"id":"call_1","result":{...}}`. Это простой транспорт, не MCP-сервер. Сообщения MaRS направляются в stderr.

## Единицы и физические соглашения

- Поле — T; время оси — s от подготовки состояния при `t=0`; частота, D, E и J — Hz; температура — K; гауссова и лоренцева ширины — FWHM в T.
- `frame = [alpha, beta, gamma]` — общие углы ZYZ в радианах. Популяции задаются в молекулярном XYZ-базисе, не в лабораторном. Все тензоры имеют общую систему главных осей, как в notebook.
- High-J: `H/h = (muB/h) B·g·S + S·D_tensor·S`, S = 1. `g` — число или три главных значения. Moderate-J: `H/h = (muB/h) B·(g1*S1 + g2*S2) + S1·(J*I + D_tensor)·S2`; `g1,2 = g0 +/- delta_g/2`. Положительный J соответствует энергии триплета выше синглета для чистого обмена. Отрицательные D, E, J допустимы.
- `D_tensor = diag(-D/3+E, -D/3-E, 2D/3)`, `|E| <= |D|/3`. В moderate-J это тензор межспинового взаимодействия. Гипертонкие взаимодействия здесь не включены.
- High-J контекст: молекулярные `[Tx, Ty, Tz]`, потери из этих состояний, тепловые переходы между соседями в `multiplet`-базисе. Moderate-J: `[S, Tx, Ty, Tz]`, потери из них, тепловые связи 1↔2, 1↔3, 2↔4, 3↔4 (`tau_outer`) и 2↔3 (`tau_inner`) в **энергетически упорядоченном eigen-базисе**, а не product-базисе. MaRS применяет свою температурную коррекцию к `thermal_rates`.
- Все `tau_*` и `rise_time_us` — µs. Скорость `k = 1e6/tau` s⁻¹. **`null` для `tau_*` означает строго нулевую скорость**, что удобно для сравнения 1D/2D; ноль как время жизни запрещён. Все времена жизни контекста должны быть указаны.
- `rise_time_us` включает эмпирическую поправку `S(B,t) - S(B,0)*exp(-t/T_rise)` перед нормировкой. При обрезанной временной оси всё равно вычисляется истинный `S(B,0)`. Это не множитель `(1-exp(-t/T_rise))` и не дополнительный канал рождения популяций.

## Популяции, нормировка и настройки

`population_mode="notebook"` воспроизводит исходные соглашения: high-J 1D — `(p-min(p))/(max(p)-min(p))`, с равномерным fallback при равных весах; high-J 2D — исходные веса; moderate-J 1D/2D — `p/max(p)`, с равномерным fallback при нулевых весах. Поэтому для сравнения high-J 1D/2D с одинаковой поляризацией явно задайте `population_mode="raw"` в обоих вызовах либо передайте эффективные веса из метаданных. Другие доступные режимы — `minmax` и `max`. Веса в [0,1] не трактуются автоматически как нормированные вероятности.

По умолчанию сигнал сохраняется без амплитудной нормировки (`normalization="none"`). `maxabs` делит весь спектр/карту на общий максимум модуля, сохраняя E/A-знаки; отдельная нормировка каждого временного среза не применяется.

Настройки по умолчанию: частота 9.8e9 Hz, 80 K, `mesh=25` для обеих сеток, CPU, float64, гармоника 0 (поглощение). `harmonic=1` — первая производная по полю. `device="auto"` выбирает доступную CUDA, иначе CPU; явно запрошенная недоступная CUDA даёт понятную ошибку. Никакие значения параметров не подставляются из старого notebook.

Оси задаются как `{"start":0.325,"stop":0.37,"points":101}` или `{"values":[...]}`. Они должны быть строго возрастающими; один временной срез допускается. Частота 9.8 GHz записывается как `9.8e9`, время 1 µs как `1e-6`, поле 350 mT как `0.350`.

## Результат и воспроизводимость

По умолчанию результаты сохраняются в `results/mars_simulations` относительно текущей рабочей директории процесса. Запускайте агент или CLI из корня проекта, открытого в VS Code. Каталог создаётся автоматически; `output_dir` и `--output-dir` позволяют явно задать другое расположение.

Каждый инструмент сохраняет NPZ, JSON с параметрами/версиями и, по умолчанию, PNG. Результат содержит абсолютные пути, форму массива, порядок осей, диапазоны, эффективные популяции и `spin_model`. NPZ содержит `fields_T`, `times_s` для 2D, `raw_spectrum`, `spectrum`, `metadata_json`; читается через `numpy.load(path, allow_pickle=False)`. `raw_spectrum` уже включает rising-поправку, если она включена, но ещё не амплитудную нормировку. Карта всегда имеет форму **(time, field)**.

`output.include_data=true` дополнительно возвращает массивы в JSON только для ≤10000 значений. По умолчанию массивы остаются в файлах, чтобы не занимать контекст агента. `output.name` — префикс имени; уникальный суффикс предотвращает перезапись. Каталог артефактов задаётся приложением, а не аргументами агента.

Кэш хранит до четырёх расчётных объектов; его ключ включает весь гамильтониан, ширины, настройки и **всю** полевую ось. Изменение контекста не переиспользует старые популяции. Один `SimulationEngine` выполняет вызовы последовательно. По умолчанию он устанавливает два CPU-потока PyTorch; это настройка процесса. Лимит выходной карты — 1e6 точек, изменяемый через `SimulationEngine(max_points=..., threads=..., cache_size=...)`. Для очистки используйте `engine.clear_cache()`.

## Окружение и проверка

Рекомендуемая основа: Python 3.11, MaRS-epr 0.0.5.post5. Для совместимости с Nevergrad при работе с notebook ранее рекомендован NumPy 1.26.4; **эти инструменты не вызывают Nevergrad или оптимизацию**. `requirements.txt` фиксирует рекомендованную комбинацию для установки зависимостей. Установку PyTorch с нужной поддержкой CUDA выполняйте отдельно согласно вашему окружению.

```powershell
python -m unittest src.mars_simulation.tests.test_simulation -v
```

Проверено: 8 тестов в имеющемся окружении Python 3.11.16 / NumPy 2.4.6 / MaRS-epr 0.0.5.post5 на CPU, mesh=4. Проверки включают прямое совпадение с конструкторами и контекстами notebook, отсутствие изменения спектра во времени при отключённых скоростях, совпадение `2d` и `2d_full`, rising-поправку, обновление кэша и артефакты всех шести инструментов. Это проверка реализации обёрток, а не исследование сходимости по сетке или физических параметров.

Важное ограничение исходного backend: в проекте ранее обнаружена проблема резонансного solver MaRS (`Fit Dir/mesh_followup_2026-10-07/README.md`). Эти инструменты используют установленный MaRS без диагностических подмен solver. Совпадение с notebook не доказывает абсолютную точность резонансных полей; для количественных выводов сохраняется необходимость проверить этот solver и сходимость конкретного набора параметров.
